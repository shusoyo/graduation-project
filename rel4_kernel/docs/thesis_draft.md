## 摘要初稿

微内核因其结构精简、访问控制边界清晰以及适合高可信构造等特点，成为操作系统形式化验证研究中的重要对象。作为能力系统微内核中的核心子系统，能力空间（Capability Space, CSpace）负责维护能力槽位、派生关系和对象访问路径，其正确性直接影响对象访问控制、能力传播以及相关系统调用的安全性。由于 CSpace 操作通常表现为“局部更新、全局约束”，传统测试方法难以系统说明其对全局不变量的保持性，因此有必要采用形式化方法对其进行建模与分析。

本文以 reL4 内核中的 `sel4_cspace` 模块为对象，研究基于 Verus 的 CSpace 形式化建模与验证方法。本文首先围绕 capability、槽项和 MDB（maximally doubly linked derivation tree）结构构建抽象状态模型，建立统一的 `CSpaceManager` 语义表示，并设计一组围绕核心更新操作展开的不变量，包括空槽一致性、MDB 链接一致性、parent-child 派生关系、badge 派生关系、untyped 子关系以及 zombie 槽约束等。在此基础上，本文对 `cte_insert`、`insert_new_cap`、`cte_move` 和 `cte_swap` 等核心操作进行规约设计与证明组织，重点讨论如何通过 changed-slots 集合、frame 条件和局部引理逐步恢复全局性质。

从当前代码结构来看，本文已经形成一套较完整的 CSpace 核心更新操作验证框架：一方面，关键 mutator 已经具备前置条件、后置条件、局部更新逻辑与不变量恢复证明；另一方面，delete、resolve 以及更高层 syscall 相关路径仍保留一定规模的 trusted contract 或外部化证明边界。因此，本文将当前成果定位为面向完整验证目标的阶段性工作，而非整个 CSpace 与 syscall 子系统的完全闭环验证。

本文的主要贡献包括：构建了 reL4 CSpace 的 Verus 抽象模型；提出了适用于能力系统更新操作的分层证明组织方法；在代码层面实现了多个核心 CSpace 操作的证明结构；分析并给出了向 delete、resolve 以及 syscall 验证继续扩展的路线。本文的工作为后续在 Rust/Verus 生态中推进更大粒度的内核子系统验证提供了基础。

- 为什么这个问题值得做形式化验证
- 为什么你选择 Verus 和 reL4 这个对象

可以按下面的逻辑展开：

#### 1.1 研究背景与意义

这一节先从微内核讲起，再落到能力系统，最后落到 CSpace。

可以直接写的思路：

- 微内核通过最小化内核功能、收缩可信计算基、隔离地址空间等方式提升系统可靠性与安全性。
- 在微内核体系中，能力对象及其派生关系决定了访问控制边界，而能力空间承担了能力存储、查找、插入、移动、删除等关键职责。
- CSpace 的正确性不仅影响对象访问路径是否正确，也影响能力传播、回收和系统调用处理的安全性。
- 由于 CSpace 操作往往表现为局部槽位更新，但又需要维护 MDB、派生关系与空槽约束等全局不变量，因此仅靠测试难以穷尽其正确性。

这一节最后一段最好收束成：

“因此，对 CSpace 核心操作进行形式化建模与机械化验证，既具有理论研究价值，也具有面向高可信内核构造的工程意义。”

#### 1.2 国内外研究现状

这一节不要写成“文献堆砌”，而要分三条线：

- seL4 与微内核形式化验证线
- Rust 形式化基础线
- Verus 与基于 Rust 的系统验证线

建议写法：

- 先介绍 seL4 作为经典验证微内核，其证明覆盖抽象规范到 C 实现的一致性，为高可信系统研究提供了代表性成果。
- 再说明 RustBelt、Prusti、Creusot、Verus 等工作推动了 Rust 生态中的形式化验证发展。
- 最后结合 Atmosphere、CortenMM、Verus 生态项目，说明“使用 Rust 构造可验证系统软件”已经成为现实方向，但围绕能力空间这类复杂内核子系统的验证工作仍然相对有限。

这一节结尾要自然引出你的选题空白：

“现有工作已经证明微内核验证与 Rust 验证具有可行性，但针对能力空间局部更新与全局约束并存特点的实现级证明组织，仍然值得进一步研究。”

#### 1.3 问题分析

这一节要把“难点”说清楚。建议写三点：

- CSpace 不是单一数据结构，而是 capability、cte、MDB、派生关系共同组成的复合系统。
- 一个操作通常只修改少数槽位，但证明时必须说明未修改部分不被破坏。
- delete、resolve、syscall 三类路径比 insert/move/swap 更复杂，因为它们牵涉递归删除、地址解析和异常传播。

如果要写得更像论文，可以加一句：

“因此，本文的关键问题不只是为单个函数补写规约，而是建立一套能够支撑局部更新类操作证明复用的统一验证框架。”

#### 1.4 本文研究内容与贡献

这里直接对应你真正做的事情，不要写满。

建议写成四点：

- 建立 CSpace 抽象状态模型与关键规格表示；
- 设计覆盖槽位、MDB 和派生关系的全局不变量体系；
- 对 `cte_insert`、`insert_new_cap`、`cte_move`、`cte_swap` 等核心更新操作实现证明组织；
- 分析 delete、resolve 以及 syscall 扩展方向中的可信边界与后续工作路线。

### 第 2 章 相关技术基础怎么写

第 2 章的目的，是给后文铺术语，不宜写得过散。  
你要让读者看到：后面的证明为什么要这样组织，是因为对象本身就长这样，工具也长这样。

#### 2.1 微内核与能力系统基础

这一节重点解释以下概念：

- 微内核只保留最核心的资源管理与隔离机制
- capability 是受控访问权的载体
- CSpace 是 capability 的组织和寻址空间
- CNode/CTE/MDB 分别解决存储、链接和派生问题

推荐写法是“概念 + 在本文中的作用”，不要只下定义。

例如：

“在本文中，CTE 不仅表示一个能力槽位，还作为 MDB 结构中的节点参与派生链维护，因此对 CTE 的更新必须同时考虑能力内容与链接字段的一致性。”

#### 2.2 reL4 与 `sel4_cspace`

这里重点不是大谈整个内核，而是说明你的研究对象位于哪里、负责什么。

建议写：

- `sel4_cspace` 是 reL4 中负责能力槽位管理、派生关系维护与能力地址解析的重要子模块；
- 它与对象创建、删除、系统调用和异常处理路径存在紧密联系；
- 本文聚焦的是其中最核心的一组 CSpace 操作及其验证组织。

#### 2.3 Rust 与 Verus

这一节建议写“为什么 Verus 适合这件事”，而不是泛泛介绍语法。

可从这几个点展开：

- Rust 的所有权模型有助于表达资源受控更新；
- Verus 支持在 Rust 风格代码中编写 `requires`、`ensures`、ghost state 和 proof；
- tracked resource 很适合表达槽位权限或受控修改；
- 循环不变式、终止性约束、proof lemma 使得实现级验证可被机械检查。

#### 2.4 本文验证风格

这一节非常重要，因为它能把你的论文方法讲“成体系”。

建议把本文风格总结成三点：

- 抽象状态驱动：先定义 `CapSpec`、`SlotEntrySpec`、`CSpaceManager`
- frame 条件驱动：重点刻画 changed slots 与未修改区域保持性
- trusted bridge 驱动：通过 runtime helper 与 trusted contract 连接运行时代码和抽象语义

### 第 3 章 验证对象与问题分析怎么写

这一章要正式进入“你的系统”，是全文从背景走向方法的过渡。

#### 3.1 模块职责分析

这里建议结合代码结构写：

- `mod.rs` 汇总了 `impl_base`、`impl_insert`、`impl_move`、`impl_swap`、`impl_delete`、`impl_resolve`、`spec_proof` 和 `spec_util` 等部分；
- 其中 `spec_proof` 承担抽象规格与 ghost 建模角色；
- `spec_util` 负责局部规格函数、预期结果与证明辅助；
- 各 `impl_*` 文件则对应不同操作路径的实现级证明。

这一节能体现你的工程组织能力，不只是算法能力。

#### 3.2 数据结构与抽象表示

这里重点写 `spec_proof.rs` 中已经出现的抽象对象：

- `CapSpec` 用于抽象 capability 的种类、对象、权限、badge、cnode 参数和 untyped 参数；
- `SlotEntrySpec` 用于抽象槽位中的 capability 及 MDB 前后继关系；
- `CSpaceManager` 则将整个槽位域、查询关系和不变量统一收拢为一个可验证的抽象管理器。

这一节要强调：  
本文并不是直接对所有 runtime 结构逐字段证明，而是先建立一个与实现对应的抽象视图，再围绕该视图展开验证。

#### 3.3 当前代码中的完成边界

这一节最好写成一张表，再配文字说明。

可以直接采用以下判断：

- `insert`、`move`、`swap`：已具备较完整规约、局部修改表达和不变量恢复结构，是当前最完整的验证成果；
- `resolve`：已具备后置条件、循环不变式和终止性约束，说明地址解析逻辑已经进入直接证明阶段，但仍较强依赖 trusted bridge；
- `delete`：仍存在较多 `external_body` 和外部化步骤，尚未形成同等强度的完整证明闭环。

这里务必要避免“全部完成”这种表述。

### 第 4 章 形式化建模与验证框架怎么写

这一章是论文的核心方法章。  
如果第 5 章讲“证明了什么”，那第 4 章讲的就是“凭什么能这样证明”。

#### 4.1 抽象状态建模

按“对象视图逐步提升”的方式写：

- 从 capability 抽象出 `CapSpec`
- 从槽位抽象出 `SlotEntrySpec`
- 从槽位集合与查询关系抽象出 `CSpaceManager`

这一节可以突出两个点：

- 抽象模型保留了证明所需的关键语义，例如对象种类、badge、MDB 链接和 cnode 参数；
- 抽象模型主动隐藏了与当前证明无关的实现细节，以降低证明复杂度。

#### 4.2 不变量体系设计

建议每个不变量都用“定义对象 + 为什么必要”来写。

例如：

- 空槽一致性：保证空槽不携带有效 capability 语义；
- MDB 链接一致性：保证前驱后继关系互相匹配，避免断链和自环；
- parent-child 派生关系：保证派生树结构不被非法更新破坏；
- badge 链关系：保证 revocable 与 first_badged 标志语义一致；
- untyped child 关系：保证 untyped 派生边界清晰；
- zombie 相关约束：为删除路径和资源回收语义提供前提。

这一节不要只列名字，必须解释“不变量在什么操作里会被破坏，又如何被恢复”。

#### 4.3 changed-slots 与 frame 条件

这是你论文里很值得强调的亮点。  
可以把它写成本文方法上的一个核心设计：

- 一个 CSpace 操作通常只影响有限个槽位；
- 因此本文不对整个全局状态做无差别重建，而是先刻画 patch set；
- 然后分别证明受影响槽位满足预期，未受影响槽位保持 frame 性质；
- 最终由局部正确性组合出整体 `wf()` 恢复。

如果你想让论文更像“有方法”，这一节一定要写细。

#### 4.4 trusted bridge 与可信边界

这一节建议专门解释一个常见误解：  
trusted 并不意味着“没有验证”，而是意味着“这部分语义当前以内嵌合同或外部公理的形式被假定为正确”。

这里可以写：

- `trusted_contracts`、`external_body`、`uninterp spec fn` 共同构成当前受信边界；
- 它们的作用是把 runtime 数据结构、异常值、cap 字段读取等低层语义桥接到抽象证明层；
- `impl_base` 更像 manager 层的基础设施 trusted 封装；
- `resolve` 路径则更直接依赖 bridge 语义，因此对底层合同的耦合更紧。

### 第 5 章 核心更新操作验证实现怎么写

这一章最容易写出“工作量”，也是答辩时老师最愿意看的部分。  
建议写法是：每个函数都按“语义目标 - 修改槽位 - 证明难点 - 恢复过程”四步展开。

#### 5.1 `cte_insert`

建议重点写：

- 语义目标是在目标空槽插入新能力，并维护源槽与派生链关系；
- 受影响的槽位通常包括 `src_slot`、`dest_slot` 以及可能存在的 `old_next`；
- 证明时不仅要说明 `dest_slot` 获得预期 capability，还要说明源槽内容、MDB 前后驱和 revocable 语义被正确修补；
- 通过局部 expected entry 和 changed-slots 组合，最终恢复全局不变量。

这一节可以明显体现你已经不是只写规约，而是在做“结构化不变量恢复”。

#### 5.2 `insert_new_cap`

这一节可以写成对 `cte_insert` 的一个变体分析：

- 二者共享局部 patch 与 frame 思路；
- 但 `insert_new_cap` 对 parent、original、slot 初始状态的约束组织方式有所不同；
- 因此证明复用的重点在于共同引理与不同 expected entry 的切换。

#### 5.3 `cte_move`

这一节要突出“移动比插入更复杂”，因为它同时涉及源槽清空和目标槽继承。

建议写：

- 操作不仅要保证目标槽得到原能力，还要保证源槽被置空；
- 与此同时，原有邻接关系需要在前驱与后继之间重新修补；
- 因此证明的重点是避免断链、自环与无效回指。

#### 5.4 `cte_swap`

这一节是很好的“复杂度展示点”。

建议强调：

- swap 是对称更新，不再是单向插入或迁移；
- 两个槽位原本都可能处于非空状态，并各自拥有不同邻接环境；
- 因此需要处理更多分类讨论，例如相邻、非相邻、重合边界和前后驱归一化问题；
- 这一部分体现了本文验证框架在复杂局部修改场景下的适应性。

#### 5.5 小结怎么写

这一章结尾不要只重复函数名，而要升华成方法结论：

“通过对 insert、move 和 swap 的验证实现可以看到，本文建立的抽象状态、不变量体系与 changed-slots 驱动的证明组织方法，能够较稳定地支持 CSpace 局部更新类操作的实现级验证。”

### 第 6 章 未完成路径与扩展方向怎么写

这一章不是“承认没做完”，而是“展示你知道剩下的难点在哪”。  
只要写得好，反而会显得你对课题掌控得比较清楚。

#### 6.1 delete 路径

建议写：

- delete 涉及 finalise、cleanup、zombie 递归化简、后处理等过程；
- 其证明难点不只是修改槽位，而是伴随对象生命周期、递归删除和异常分支；
- 当前代码中仍存在 `external_body` 与 trusted helper，说明这一路径尚未完全展开为实现级机械证明；
- 但已有的 manager 层基础设施和不变量体系为后续补齐 delete 提供了条件。

#### 6.2 resolve 路径

这一节一定要写准，不要再把它写成“几乎没做”。

推荐表述：

- `resolve_address_bits` 已经具备显式后置条件、循环不变式与终止性约束；
- 这说明地址解析路径已经进入直接证明阶段，而不是单纯的 stub；
- 但其证明过程更直接依赖异常值、cap 字段读取、slot 查找等 trusted bridge 合同；
- 因此当前更适合将 resolve 定位为“已形式化并完成关键证明骨架的辅助路径”，而非与 `insert/move/swap` 同等成熟的 manager 级闭环成果。

#### 6.3 syscall 扩展方向

这一节可以从“为什么现在还没接上去”来写：

- syscall 层需要把参数解码、异常传播、capability 查找和具体 mutator 调用串起来；
- 一旦要验证 syscall，就不能只证明单个 CSpace 操作，还要证明调用前后错误码、异常分支和参数合法性；
- 因此 syscall 级验证天然依赖 delete、resolve 等底层路径进一步收口。

### 第 7 章 分析与讨论怎么写

这一章的作用是把前面的技术内容“收拢成评价”。  
它不是重复第 5 章，而是回答：这项工作到底完成到什么程度、和已有工作相比有什么特点、局限在哪。

#### 7.1 当前成果定位

建议明确写：

- 本文已经完成 CSpace 核心更新操作的一组代表性证明；
- 已形成从抽象建模、不变量设计到实现级证明组织的基本闭环；
- 当前成果更适合定位为“面向完整验证的阶段性成果”，而不是整个 CSpace 乃至 syscall 子系统的最终完备验证。

#### 7.2 与已有工作的关系

这里可以做两个比较：

- 与 seL4 经典验证相比：本文验证范围更小，但更贴近 Rust/Verus 生态下的实现级实验；
- 与 Verus 项目生态中的其他系统工作相比：本文聚焦能力空间与局部更新不变量恢复，具有较强的结构化状态操作特征。

#### 7.3 局限性

这一节不要怕写，写出来反而专业。

建议列出：

- 仍存在一定 trusted surface；
- delete 与 syscall 级路径尚未完全闭合；
- 当前结果主要集中于核心 mutator，而非整个内核能力系统全链路。

### 结论怎么写

结论控制在一到两页最稳。

- 第 1 段总结研究背景和本文目标；
- 第 2 段总结已经完成的工作；
- 第 3 段说明当前局限；

## 第 1 章 绪论初稿

### 1.1 研究背景与意义

随着高可信系统、关键基础设施和嵌入式安全平台对基础软件可信性的要求不断提高，微内核因其最小化设计、强隔离能力与较小的可信计算基，成为形式化验证研究的重要载体。与宏内核相比，微内核通常只保留线程调度、地址空间管理、进程间通信以及访问控制等最基本机制，因此更适合围绕关键安全属性开展系统化分析。

在微内核体系中，能力系统是一种典型的访问控制机制。能力不仅表示对象的引用关系，还编码访问权限与操作边界，因此能力的派生、复制、移动、删除和解析都直接关联安全属性。在 seL4/reL4 一类以内核对象和能力传播为核心的系统中，CSpace 负责组织这些能力槽位与派生关系，是连接对象访问控制与系统调用逻辑的关键中间层。

然而，CSpace 的验证并不是一个简单的数据结构正确性问题。以插入、移动和交换为代表的核心操作虽然往往只修改极少数槽位，但这些修改会影响 MDB 双向链接、派生链语义、badge 传播关系以及后续解析行为。因此，CSpace 操作天然具有“局部更新、全局约束”的特征。传统测试方法能够覆盖一部分操作路径，却很难系统性证明：在所有满足前置条件的情况下，更新后的状态依然保持全局结构与语义不变量。

近年来，Rust 语言凭借所有权与借用机制，为系统软件提供了较强的内存安全基础；Verus 则在 Rust 的语法与类型体系之上引入了形式化规格与证明机制，使研究者能够在接近实现代码的层面表达并检查程序性质。对于 reL4 这样正在 Rust 生态中演化的系统而言，基于 Verus 对 CSpace 进行建模和验证，不仅具有理论价值，也具有明确的工程意义。

### 1.2 国内外研究现状

操作系统形式化验证领域最具代表性的工作之一是 seL4。Klein 等人在 *seL4: Formal Verification of an OS Kernel* 中首次展示了通用微内核功能正确性验证的可行性，奠定了“以内核小规模机制为对象进行完整证明”的研究路线。随后，*Comprehensive Formal Verification of an OS Microkernel* 进一步扩展了对 seL4 的 assurance story，说明功能正确性之外，还可以继续考虑访问控制、信息流、二进制正确性等更高层保证。*From L3 to seL4* 对 L4 系列微内核长期演进中的设计经验进行了总结，说明小内核结构、能力接口和验证友好性之间存在紧密联系。*seL4 Enforces Integrity* 与 *Translation Validation for a Verified OS Kernel* 则分别从安全性质和编译链保证两个方向补充了内核验证版图。

在 Rust 和 Verus 方向，*RustBelt* 为 Rust 语言的安全承诺提供了形式化基础。Lattuada 等人的 *Verus: Verifying Rust Programs using Linear Ghost Types* 给出了 Verus 的核心设计思想，展示了如何在 Rust 中结合 ghost state、线性资源和前后置条件表达复杂程序性质。随后，*Verus: A Practical Foundation for Systems Verification* 进一步说明 Verus 已具有支撑较大规模系统验证任务的工程潜力。

围绕 Verus 的项目生态，也已经形成了一系列具有代表性的案例。例如 IronFleet 和 IronSync 展示了面向分布式系统和并发复制组件的验证方法；PoWER 展示了面向持久化存储正确性的规约组织思路；CortenMM 展示了内存管理组件验证的工程实践；Atmosphere 则体现了在 Rust 中构建可验证内核的探索方向。这些工作说明，Verus 已经能够支撑真实系统组件的验证开发，而不只是停留在小规模样例层面。

尽管如此，reL4 中的 CSpace 仍具有其自身特殊性。它不是单纯的链表或树结构验证问题，也不仅是 syscall 接口规约问题，而是一个同时涉及 capability 语义、槽位关系、派生边语义、解析过程和内核调用路径的复合验证对象。现有研究为本文提供了方法论、结构化证明思路与工程经验，但并不能直接替代对 `sel4_cspace` 的专门建模和分析。因此，围绕 reL4 CSpace 构建适配 Verus 的验证框架，仍具有明确的研究意义。

### 1.3 问题分析

结合当前代码可以看出，CSpace 验证至少面临以下几类问题。

首先，CSpace 的核心更新操作具有典型的局部 patch 特征。插入、移动和交换在实现上只涉及少量槽位，但它们对相邻节点、派生关系和后续解析语义产生影响，因此证明的重点不是“改了哪个值”，而是“在仅修改这些槽位的前提下，全局不变量如何恢复”。

其次，CSpace 中存在多类结构与语义不变量。除了最直观的前驱、后继链接一致性之外，还包括 parent-child 派生关系、badge 派生关系、untyped 相关约束、zombie 槽位语义以及 root cnode 解析相关语义。这些性质往往相互依赖，使证明不能只围绕单一结构展开。

再次，运行时代码直接操作 `cte_t`、`cap`、`mdb_node` 等底层结构，而证明更适合围绕抽象状态进行。因此，必须在运行时视图与抽象规格视图之间建立稳定桥接。这一桥接层若缺乏控制，会导致 trusted surface 过大，从而削弱“已验证”结论的强度。

最后，如果研究目标继续向完整 CSpace 验证乃至 syscall 验证推进，那么 delete 与 resolve 两类路径是无法绕开的。delete 涉及递归删除、异常传播、zombie 规约与清理逻辑；resolve 则涉及 cnode guard、radix、bitsRemaining 和 lookup fault 等多种语义分支。由此决定了本文不能简单把几个核心 mutator 的证明等同于整个子系统的完成。

### 1.4 本文研究内容

围绕上述问题，本文主要开展以下工作。

第一，对 reL4 中的 CSpace 进行抽象建模。本文引入 capability、槽位项和 CSpace 管理器等抽象结构，统一表达运行时槽位与派生关系的语义。

第二，围绕 CSpace 核心操作设计不变量体系。本文从空槽性质、MDB 链接一致性、派生边语义以及解析相关约束等方面构建 `wf()` 风格不变量，为后续证明提供统一目标。

第三，对 `cte_insert`、`insert_new_cap`、`cte_move` 和 `cte_swap` 等关键更新操作进行规约设计与证明组织。这些操作是 CSpace 中最核心、最具代表性的 mutator，也是向 delete 和 syscall 层扩展的基础。

第四，结合当前代码结构分析 delete、resolve 与 syscall 方向的未完成部分，给出向完整验证推进的后续路线。本文因此将当前成果界定为“面向完整验证目标的阶段性成果”。

### 1.5 本文贡献

本文的主要贡献可以概括为以下三点。

1. 建立了 reL4 CSpace 的 Verus 抽象模型，统一描述 capability、槽项和 MDB 结构。
2. 提出了一种围绕 changed-slots、frame 条件和不变量恢复展开的分层证明组织方法。
3. 在代码层面实现了多个核心 CSpace 更新操作的证明结构，并分析了向 delete、resolve 和 syscall 扩展的技术路线。

### 1.6 论文结构安排

本文其余章节安排如下。第 2 章介绍微内核、能力系统、Rust 与 Verus 等背景知识。第 3 章分析 `sel4_cspace` 的职责、结构和当前验证边界。第 4 章给出 CSpace 的抽象建模、不变量体系与证明框架。第 5 章详细讨论 `insert`、`move` 和 `swap` 等核心 mutator 的规约和证明组织。第 6 章分析 delete、resolve 和 syscall 方向的未完成路径与扩展策略。第 7 章从代码结构角度讨论当前工作状态、意义与局限。第 8 章总结全文并展望后续工作。

## 第 2 章 相关技术基础初稿

### 2.1 微内核与能力系统

微内核通过把大部分服务移到用户态、仅在内核中保留最小化机制，从而在结构上更有利于构建高可信系统。能力系统则为内核对象访问提供统一表示：一个 capability 同时携带对象引用信息与访问权限信息，因此 capability 的分发与维护直接构成系统安全边界的一部分。对于 reL4 这样的系统而言，CSpace 并不是简单的对象表，而是 capability 组织、派生和访问控制的基础层。

### 2.2 seL4/reL4 与验证背景

seL4 相关工作证明了微内核是最适合开展形式化验证的系统软件对象之一。本文在研究目标上与 seL4 一脉相承，即都关注内核关键机制的高保证构造；但在方法层面，本文并不沿用 Isabelle/HOL 风格的大规模整体证明路线，而是探索基于 Rust/Verus 的更贴近实现代码的证明方式。reL4 则为这种探索提供了实际载体，因为其代码生态与 Rust 更紧密结合。

### 2.3 Rust、RustBelt 与 Verus

Rust 通过所有权、借用与生命周期机制减少了系统软件中的内存错误风险；RustBelt 从语义层面对这些安全承诺进行了形式化分析。Verus 则在 Rust 语法基础上引入规范函数、proof function、ghost state 和前后置条件，使开发者能够在接近实现代码的层面书写规格与证明。对本文而言，Verus 的关键价值在于它允许“规格与实现共存”，从而更适合处理像 CSpace 这样证明与真实实现紧密耦合的子系统。

### 2.4 与 Verus 项目生态的关系

从 Verus 已公开的项目来看，系统验证已经覆盖分布式系统、并发复制、持久化存储、内存管理以及内核探索等方向。IronFleet 和 IronSync 展示了模块化证明如何服务于复杂系统；PoWER 说明了如何围绕高层语义规约组织底层实现证明；CortenMM 展示了系统级内存管理的验证落地；Atmosphere 则为“Rust 内核可验证化”提供了探索性参考。本文与这些工作的共同点，是都强调可信边界显式化和分层证明；不同点在于本文的对象是 capability 系统中的 CSpace 子模块。

## 第 3 章 验证对象与问题分析初稿

### 3.1 `sel4_cspace` 模块职责

从当前代码结构看，`sel4_cspace` 负责 capability 相关的核心管理逻辑，包括插入、派生插入、移动、交换、删除、撤销、以及 cnode 地址解析等功能。这些操作既服务于对象级管理，又构成更高层 syscall 的基础调用单元。因此，如果未来希望继续验证 syscall，则必须先让 CSpace 层具备稳定规约和可复用证明基础。

### 3.2 关键数据结构与抽象语义

运行时层面，CSPACE 操作主要围绕 `cte_t`、`cap` 和 `mdb_node` 等结构展开；抽象层面，代码中则通过 capability 规格、slot entry 规格以及 CSpace 管理器规格统一表达相关语义。从当前证明结构看，抽象状态并不是对运行时结构的完全替代，而是一个与运行时实现并行存在、通过 trusted bridge 联系起来的规格视图。

### 3.3 当前代码中已经较成熟的部分

从代码结构判断，当前已经较成熟的部分主要集中在核心 mutator：

- `cte_insert`
- `insert_new_cap`
- `cte_move`
- `cte_swap`

这些操作都已经表现出明显的 Verus 风格：函数本体具有显式的前置条件和后置条件；实现过程中使用 tracked permission 或等价桥接机制；证明部分围绕局部 postcondition、changed-slots 分析以及一系列 `lemma_preserves_*` 引理恢复全局 `wf()`。

### 3.4 当前代码中仍然明显未完成的部分

同样只从代码结构判断，可以看出以下路径仍未形成与核心 mutator 同等程度的闭环：

- delete 路径保留较多 `#[verifier::external_body]`
- resolve 路径中存在一组 admitted contract 风格的证明边界
- runtime bridge 与 trusted contracts 仍承担较重职责

因此，论文中必须把当前工作定位为“以核心更新操作为中心的阶段性验证成果”，而不是“整个 CSpace 全部完成验证”。

## 第 4 章 CSpace 的形式化建模与验证框架初稿

### 4.1 抽象状态建模

本文在 Verus 中围绕 capability、slot entry 和 CSpace 管理器构建抽象状态模型。该模型的目的不是复刻每一个底层位字段，而是在足以支撑证明的层面上表达 capability 类型、关联对象、region、权限、badge、cnode 数据、untyped 数据以及 MDB 链接语义。通过这种建模方式，证明可以围绕抽象状态演化展开，而不必直接在每条位级读写上展开。

### 4.2 全局不变量体系

结合当前代码结构，本文所依赖的不变量体系至少包括以下几类：

- 空槽一致性
- MDB 双向链接一致性
- parent-child 派生关系
- badge 派生关系
- untyped 子关系
- zombie 相关约束
- 解析过程相关性质

这些不变量共同构成 `wf()` 风格的系统状态约束。其核心思想不是孤立证明单个性质，而是把 CSpace 正确性组织为一个由多种结构与语义性质共同支撑的整体。

### 4.3 changed-slots 与 frame 条件

从当前证明风格可以看出，本文采用了一个很关键的组织方法：围绕实际被修改的槽位集合组织证明。对于 `cte_insert`，该集合通常包括 `src`、`dest` 和可能存在的 `old_next`；对于 `cte_move`，则需要纳入源槽、目标槽及其原邻居；对于 `cte_swap`，则需要纳入两个目标槽及相关邻居。通过显式刻画 changed-slots，可以先证明“未修改区域不变”，再证明“修改区域满足期望语义”，最终合成为全局不变量保持结论。

### 4.4 不变量恢复而非一次性证明

本文所采用的不是“在每个 mutator 末尾一次性推出全部结论”的写法，而是“分量恢复”的写法。也就是说，证明先建立局部后置条件，再依次恢复空槽性质、链结构性质、派生边语义和解析相关性质，最后回到统一的 `wf()`。这种方式更贴合大规模系统验证的工程现实，也更适合 CSpace 这种局部修改影响多个语义层面的对象。

### 4.5 trusted bridge 与证明边界

由于运行时代码直接操作真实内核结构，当前代码中存在一层较明确的 trusted bridge。它的作用是为证明层提供稳定抽象接口，但它也意味着：当前工作不能被表述为“完全消除了 trusted 假设”。因此，本文必须在方法章节中主动说明可信边界，而不是在结果章节中回避这一点。对于评审而言，清楚标出 trusted surface，往往比含糊宣称“已经全部证明”更有说服力。

## 第 5 章 CSpace 核心更新操作的验证实现初稿

### 5.1 `cte_insert`

从当前代码可以看出，`cte_insert` 已具有较完整的 Verus 风格规约。其前置条件要求旧状态满足全局 `wf()`，源槽与目标槽均位于 slot domain 中，目标槽为空，并要求新 capability 与源 capability 在相关语义上保持兼容。其后置条件要求更新后状态仍满足 `wf()`，并且目标槽包含期望 capability。

实现上，`cte_insert` 主要执行三类局部更新：读取源槽 capability 与原 `next`；向目标槽写入新 capability 并建立与源槽、原后继之间的关系；必要时修补原后继的 `prev`。证明部分则围绕局部 postcondition、expected entry、changed-slots 集合与多类 `lemma_preserves_*` 引理展开，最终恢复全局 `wf()`。这一结构已经非常适合作为论文中“核心验证案例”的主展示对象。

### 5.2 `insert_new_cap`

`insert_new_cap` 可以被视为 `cte_insert` 的一个特化版本，它以 parent 为语义中心建立新的 child 槽位。虽然具体语义不同，但从证明组织上看，它延续了同样的结构：限定局部修改范围，建立 expected entry，再恢复全局不变量。论文中可以把它用来说明：本文提出的 changed-slots 与 frame 风格并不是只对单个函数有效，而是对同一类 capability mutator 具有复用价值。

### 5.3 `cte_move`

`cte_move` 的目标是在保持能力语义的前提下，将源槽内容迁移到目标槽，并把源槽清空。从代码组织上看，它除了需要处理目标槽写入和源槽清空之外，还必须修补原前驱和后继的链接关系，因此比插入类操作更强调“链结构修补”的正确性。当前证明不仅关注更新后的 `wf()`，还明确约束无自环等更细粒度的结构性质，这说明本文在证明目标上已经超出了简单的值级正确性。

### 5.4 `cte_swap`

`cte_swap` 是当前最复杂的核心 mutator 之一。它需要在两个槽位之间交换 capability 和相关标志，同时正确处理两侧的前驱与后继，并兼顾相邻节点重合、前后关系对称等多种特殊情形。从当前代码结构判断，这一操作的证明复杂度显著高于 `cte_insert` 与 `cte_move`，因为它不仅要处理两个中心槽位，还要处理由二者引出的多个邻接修补分支。

正因为 `cte_swap` 的结构复杂，它非常适合在论文中用来展示本文方法的强度：如果一套证明框架能够支撑 `swap` 这样具有较多分支的对称更新操作，那么它在方法上就已经具有相当的说服力。

### 5.5 本章小结

本章所讨论的四个操作体现出一个共同特征：它们都采用“局部更新 + changed-slots + 分量不变量恢复”的模式组织证明。由此可见，本文当前阶段的真正成果不只是“证明了几个函数”，而是已经形成一套可复用的 CSpace mutator 验证套路。这为后续继续纳入 delete、resolve 和 syscall 层提供了方法基础。

## 第 6 章 未完成路径与向完整验证的扩展

### 6.3 syscall 扩展方向

syscall 方向目前最合理的论文写法，不是宣称“已经验证 syscall”，而是说明：

- CSpace 核心 contract 已经在形成；

这会让论文呈现出一种很成熟的研究姿态：不是说自己已经做完，而是清楚知道下一步怎么做。

综合来看，delete、resolve 与 syscall 并不是“没有开始”，而是处于不同程度的阶段性推进中。论文中最合适的写法，是把当前工作定位为“以核心 mutator 为中心建立验证框架”，并把这些未完成路径纳入未来工作与扩展路线中。

## 第 8 章 总结与展望初稿

本文围绕 reL4 内核中的 CSpace 管理逻辑，研究了基于 Verus 的形式化建模与验证方法。本文从 capability、槽项和 MDB 结构出发，构建了统一的抽象状态模型和一组围绕 `wf()` 展开的关键不变量，并在此基础上对 `cte_insert`、`insert_new_cap`、`cte_move` 与 `cte_swap` 等核心更新操作实现了系统性的规约与证明组织。通过 changed-slots、frame 条件和不变量恢复思路，本文形成了一套适用于 CSpace mutator 的分层验证方法。
